# 신박한 캘린더 — 마감일이 아니라 준비 시작일을 알려주는 AI 캘린더

공지(텍스트/이미지)를 넣으면 Gemini API가 요약·중요도·일정·할일을 자동으로 뽑아내고,
**"이건 준비가 며칠 걸리는 일인지"까지 판단해서 준비 시작일을 역산**해 캘린더에 막대로 그려줍니다.
사용자가 "캘린더에 추가"/"할일에 추가"를 누른 것만 저장됩니다.

기존 일정 관리 앱들이 공지에서 날짜 하나를 뽑아 **점(point)** 을 찍는다면,
이 앱은 준비 기간까지 계산해서 **막대(bar)** 를 그립니다. 여러 준비 기간이 겹치면
그 주가 바쁠 거라는 것도 캘린더에서 바로 보입니다.

## 폴더 구조
```
smart-calendar/
├── backend/
│   ├── server.js                    # Express 진입점 (프론트 정적파일도 같이 서빙)
│   ├── routes/api.js                # 분석/확인/캘린더/할일/브리핑 API
│   ├── services/geminiService.js    # 공지 분석 (요약·중요도·일정·needsPrep 추출)
│   ├── services/leadTimeService.js  # 준비기간 판단 + 단계 분해 (차별화 핵심)
│   ├── services/pushService.js      # 웹푸시(VAPID) 발송
│   └── models/                      # Notice, ScheduleEvent(준비기간·단계 지원), Todo, PushSubscription
└── frontend/
    └── index.html                   # 캘린더/공지/알림/일정 관리 4탭, 월 그리드, 다크모드
```

## 1. 실행 방법

```bash
cd backend
npm install
cp .env.example .env
```

`.env` 파일 채우기:
- `GEMINI_API_KEY` — https://aistudio.google.com/apikey
- `MONGODB_URI` — MongoDB Atlas 연결 문자열 (Network Access에 0.0.0.0/0 등록 필요)
- `GEMINI_MODEL` — 기본값 `gemini-3.1-flash-lite` (2.5-flash-lite는 신규 키에서 404남)

```bash
npm start
```

`http://localhost:4000` 접속.

## 2. 핵심 플로우 (2단계: 분석 → 확인)

1. **분석 (미리보기, 저장 안 됨)**
   - 텍스트: `POST /api/notices/analyze-text { text }`
   - 이미지: `POST /api/notices/analyze-image` (multipart, field: `image`)
   - 응답: `{ sourceType, rawContent, result: { summary, priority, category, event, todo, needsPrep, leadTimeDays, leadTimeSource } }`
   - `event.startDate`는 이미 준비 시작일로 당겨져 있고, `event.originalStartDate`에 원래 날짜가 남습니다.
     `event.steps`에는 준비 단계 초안이 들어있습니다.
2. **확인 (사용자가 버튼을 눌러야 저장)**
   - `POST /api/notices/confirm { sourceType, rawContent, summary, priority, category, addEvent?, addTodo? }`
   - `addEvent`/`addTodo`를 보낸 것만 실제로 `ScheduleEvent`/`Todo`에 저장됨
   - `addEvent.leadTimeDays`에 사용자가 조정한 값을 넣어 보내면 **서버가 시작일과 단계 계획일을 다시 계산**합니다.
     날짜 계산을 서버 한 곳에만 두려는 것이라, 프론트는 일수만 보내면 됩니다.
   - `addEvent.stepTitles`에 단계 제목 배열을 같이 보내면 표준 템플릿 대신 그 구성으로 저장됩니다
     (기억해둔 단계 구성을 재사용할 때 씁니다).
   - "캘린더에 추가"와 "할일에 추가"는 각각 별도로 호출 (둘 다 누르면 Notice 레코드가 2번 생기지만, 상관없음 — 히스토리 겸용)

## 3. 준비기간 역산 (이 서비스의 핵심)

`services/leadTimeService.js`가 담당합니다. 3단계로 값이 정해집니다.

1. **AI 초안** — Gemini가 `needsPrep`(준비가 필요한 일인가)과 `suggestedLeadDays`(며칠 걸릴까)를 냅니다.
   카테고리만 보는 게 아니라 공지 **내용의 분량**을 읽습니다. 같은 '과제'라도
   "설문 응답 제출"은 1일, "조사 보고서 A4 5장 + 발표"는 7일이 나옵니다.
2. **규칙표 보정** — 종류별 허용 범위를 벗어나면 끌어당깁니다. 규칙표는 상수가 아니라
   종류 설정(4장)에서 `buildRules()`가 매번 만듭니다. 기본 준비기간이 0일인 종류(행사·회의)는
   AI가 뭐라고 하든 `needsPrep=false`로 고정됩니다.
3. **사용자 조정** — 확인 화면에서 +/- 로 바꾼 값이 최종값이고,
   그 값은 `localStorage`에 종류별로 저장돼 다음 등록의 기본값이 됩니다.

계산식은 `준비 시작일 = 일정 시작일 − leadTimeDays` 입니다.
마감일이 아니라 **일정 시작일** 기준인 이유는, "기말고사 7/27~7/31"처럼 기간이 있는 일정에
마감일 기준으로 빼면 시험 기간 한복판에서 준비를 시작하는 꼴이 되기 때문입니다.
하루짜리 마감이면 두 계산이 같은 값이 됩니다.

준비기간이 잡히면 카테고리별 표준 단계(`STEP_TEMPLATES`)로 쪼개서 체크리스트를 만들고,
각 단계에 계획 날짜를 균등 배분합니다. 제목에 "발표"가 들어가면 카테고리보다 제목을 우선해
발표형 단계(자료조사 → 초안 작성 → 리허설 → 최종 점검)를 씁니다.

### 단계 구성도 사용자가 고치고, 그걸 기억합니다

일정 상세 → `준비 단계` 옆 **편집**에서 단계 이름 수정 / 추가 / 삭제 / 순서 변경을 할 수 있습니다.
저장하면 남은 기간에 맞춰 계획 날짜가 다시 배분되고, 이름이 그대로인 단계는 완료 체크가 유지됩니다.

"다음에도 이 구성으로 만들기"를 켜두면 그 구성을 `localStorage`에 기억했다가,
다음에 **같은 종류의 일정**이 들어올 때 표준 템플릿 대신 먼저 제안합니다.

> 기억하는 단위는 카테고리가 아니라 **단계 템플릿 종류**(`stepTemplateKey`)입니다.
> 같은 '과제'라도 발표형과 논술형은 준비 단계가 다르기 때문에, 발표 수행평가에서 고친 구성이
> 독후감에 잘못 적용되지 않습니다.
>
> 리드타임 개인화와 마찬가지로 **모델을 재학습시키는 게 아니라, 고친 값을 기기에 기억해뒀다가
> 다음에 먼저 제안하는 규칙 기반 방식**입니다. 설명할 때 이 점을 정확히 구분하는 게 좋습니다.

> 날짜 계산은 전부 UTC 기준으로 하고 "오늘"은 KST로 따로 구합니다.
> 배포 서버 타임존이 UTC라서 그냥 `new Date()`를 쓰면 한국 시각 오전에 하루씩 밀립니다.

## 4. 일정 종류 (사용자가 바꿀 수 있음)

알림 탭 범례의 **설정** 버튼에서 종류를 관리합니다. 종류 하나는 네 가지를 갖습니다.

| 항목 | 설명 |
|---|---|
| 이름 | AI 분류에 그대로 쓰입니다. "회의"를 "동아리"로 바꾸면 AI도 그 이름으로 분류합니다 |
| 색 | 미리 검증된 11색 팔레트에서 선택. 종류끼리 같은 색은 못 고릅니다 |
| 기본 준비기간 | 그 종류의 기본 리드타임. 0일이면 준비기간 없이 그 날 하루만 |
| 준비 단계 구성 | 작성형 / 발표형 / 시험형 / 학사형 / 일반 중 선택 |

추가·삭제·이름변경이 가능하고 최대 10개입니다. `기타`는 AI가 분류하지 못한 공지가 떨어지는
자리라 삭제할 수 없습니다(사용자가 지워도 서버가 다시 채워 넣습니다).

**자유도를 여기까지만 연 이유**

- 색을 완전히 자유롭게(색상 선택기) 열면 글씨가 안 읽히거나 종류끼리 구분이 안 됩니다.
  팔레트의 11색은 "어떤 색을 골라도 대비 4.0 이상, 종류 간 색차 33 이상"을 미리 계산해 확인한 값입니다.
- 종류마다 `key`(내부 식별자)와 `label`(표시 이름)을 분리했습니다. 이름을 바꿔도 key는 그대로라
  이미 저장된 일정들이 종류를 잃지 않습니다.

**동작 방식**: 프론트가 요청마다 종류 목록을 같이 보내면, 백엔드가
①Gemini 프롬프트의 분류 후보를 그 이름들로 바꾸고(개수도 목록 길이에 맞춰 달라집니다)
②AI가 돌려준 이름을 내부 key로 되돌리고 ③그 종류의 규칙으로 준비기간을 계산합니다.
종류 설정을 못 보내는 경로(iOS 단축어)는 기본 6종으로 자동 대체됩니다.

## 5. 캘린더/할일 CRUD
- `GET /api/schedule` — 전체 일정 (월 그리드 렌더링은 프론트에서 처리)
- `POST /api/schedule` / `PATCH /api/schedule/:id` / `DELETE /api/schedule/:id` — FAB(+) 버튼으로 수동 추가한 일정
  - `POST`/`PATCH`에 `leadTimeDays`를 같이 보내면 수동 일정에도 준비기간이 붙습니다.
  - `PATCH`로 `leadTimeDays`만 바꾸면 시작일과 단계 계획일이 서버에서 다시 계산됩니다
    (이미 체크해둔 단계의 완료 상태는 유지).
- `PATCH /api/schedule/:id/steps/:index` — 준비 단계 하나 완료 토글
- `PUT /api/schedule/:id/steps` — 단계 목록 전체 교체(이름 수정/추가/삭제/순서 변경).
  `{ steps: [{ title, done }] }` 형태로 보내면 계획 날짜를 새 개수에 맞춰 다시 배분합니다.
  최대 8개, 제목 30자까지. 빈 제목은 버려집니다.
- `POST /api/schedule/:id/retro` — 마감 후 회고 저장 (`feeling`: tight/ok/loose)
- `GET /api/briefing` — 오늘 브리핑. `active`(준비 중), `upcoming`(3일 내 시작), `retroPending`(회고 대기)
  - 정렬은 **임박도 + 부담** 2축입니다. 마감이 더 멀어도 준비 분량이 크고 진척이 없으면 위로 올라옵니다.
- `GET /api/todos`, `POST /api/todos`, `PATCH /api/todos/:id` — 할일 조회/추가/완료 토글

## 6. 화면 구성
- **캘린더** — 월 그리드 + 준비기간 막대 + 겹치면 레인에 쌓임(`+N건 더보기`).
  막대 색은 **일정 종류**(같은 종류 안에서도 일정마다 다른 변주), 막대 안 점은 **중요도**입니다.
  색상은 "무엇인지"를, 점은 "얼마나 급한지"를 나타내도록 채널을 분리한 것입니다
- **공지** — 텍스트/이미지 입력 → AI 분석 → 준비 시작일 미리보기 + 준비기간 +/- 조정 → 저장
- **알림** — 오늘의 브리핑(2축 정렬, 진행률 바, 회고 질문) + 전체 일정 피드
- **일정 관리** — `준비 중인 일정`(진행률·D-day) / `할일` 세그먼트. 일정을 탭하면 단계 체크리스트
- 다크모드 토글, 일정 상세에서 AI 요약 + 원본 자료 확인
- 로그인/회원가입/프로필 화면 — **주의: 현재는 UI만 있고 실제 인증 백엔드는 없음(클라이언트 상태로만 존재)**

## 7. 지금 범위에서 빠진 것
- **날짜 기반 예약 알림** — 웹푸시 인프라(구독/발송/만료정리)는 동작하지만,
  "매일 특정 시각에 D-day를 체크해서 보내는" 스케줄러(크론)는 아직 없습니다.
  지금은 일정 등록 시점에 1번 + 1분 뒤 테스트 알람 1번만 갑니다.
  진행 상황에 따라 알림 강도를 조절하는 기능은 이 크론이 선행돼야 의미가 있습니다.
- 변경 공지 자동 반영 (신청서 6번 기능) — 난이도 대비 시간 리스크가 커서 제외
- 로그인 실제 백엔드 연동 (현재 목업)
- 사용자별 데이터 분리 — 지금은 계정 개념이 없어서 모든 접속자가 같은 일정을 봅니다
