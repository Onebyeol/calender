# 신박한 캘린더

> **마감일이 아니라, 준비 시작일을 알려주는 AI 캘린더**

카카오톡·학교 홈페이지·LMS에서 온 공지를 붙여넣거나 사진으로 넘기면,
AI가 공지의 성격을 읽고 **"이 일은 언제부터 준비해야 하는가"** 를 역산해서 캘린더에 막대로 그려준다.

---

## 무엇이 다른가

일정 관리 앱에 공지를 넣으면 보통 **날짜 하나에 점을 찍는다.**
그런데 수행평가나 보고서 제출은 그 날 가서 끝나는 일이 아니라 며칠 전부터 준비해야 하는 일이다.
마감일만 캘린더에 있으면, 정작 "언제부터 시작해야 하는지"는 아무도 알려주지 않는다.

| | 일반 캘린더 / 기존 일정 AI | 신박한 캘린더 |
|---|---|---|
| 공지에서 뽑는 것 | 날짜 하나 | 마감일 + **준비 시작일** |
| 캘린더 표현 | 그 날짜에 점 | 준비기간 ~ 마감일 **막대** |
| 준비기간 | 사용자가 직접 판단 | 공지 내용의 분량·난이도를 읽고 자동 역산 |
| 겹침 | 표시 없음 | 같은 주에 준비기간이 몇 개 겹치는지 레인으로 시각화 |
| 그 기간 동안 | — | 준비 단계로 분해 + 체크리스트 |

## 주요 기능

**공지 등록** — 텍스트 붙여넣기 / 스크린샷 업로드(OCR) / 공유 시트로 자동 등록
(Android는 PWA Web Share Target, iOS는 단축어)

**분석 → 확인 2단계** — AI 결과를 바로 저장하지 않는다. 미리보기를 보여주고 사용자가 "캘린더에 추가"를 누른 것만 저장되며, AI가 잡은 준비기간을 직접 조정할 수 있다.

**화면 4탭**

| 탭 | 하는 일 |
|---|---|
| 오늘 | 일별 브리핑(임박도 + 부담 2축 정렬), 오늘의 단계·할일, 곧 준비를 시작할 일정 |
| 캘린더 | 월 그리드 + 준비기간 막대, 겹치는 일정 레인 배치 |
| 기록 | 준비 습관 통계, 진행 중/지난 일정, 마감 후 회고 |
| 설정 | 계정, 일정 종류 편집, 푸시 알림, 다크모드 |

그 밖에 준비 단계 체크리스트, 마감 후 회고, 일정 종류 커스터마이징(이름·색·기본 준비기간), 웹 푸시 알림, PWA 설치, 다크모드.

## 동작 원리

```
공지(텍스트/이미지/공유)
   ↓  Gemini 분석 — 요약·중요도·종류 분류·마감일 추출
   ↓  needsPrep + suggestedLeadDays  ← AI는 '초안'만 낸다
   ↓  종류별 규칙표가 보정
   ↓  사용자가 확인 화면에서 최종 조정
   ↓  준비 시작일 역산 → 캘린더 막대 + 단계 체크리스트
```

### 준비기간은 3단계로 정해진다

**AI 혼자 정하지 않는다.** 이 구조가 이 프로젝트의 핵심이다.

**1. AI 초안** — 카테고리가 아니라 *공지 내용의 분량과 난이도*를 읽고 판단하도록 프롬프트에 명시했다.

| 공지 내용 | 제안 준비일수 |
|---|---:|
| 설문 응답, 동의서 회신 | 1 |
| 독후감 A4 1장 | 2~3 |
| 조사 보고서 A4 5장 이상, 팀 발표 | 5~7 |
| 범위가 여러 단원인 지필평가 | 7~10 |

**2. 규칙표 보정** — 종류마다 허용 범위를 두고 AI 값이 벗어나면 잡아준다.
범위는 기본 준비일수에서 자동 계산된다(`min = 40%`, `max = min(30, max(2배, +7일))`).

| 종류 | 기본 준비일수 | 준비 필요 판단 | 단계 템플릿 |
|---|---:|---|---|
| 학사일정 | 2일 | AI 판단 | 학사형 |
| 과제 | 3일 | 항상 | 작성형 |
| 시험 | 7일 | 항상 | 시험형 |
| 행사 · 회의 | 0일 | 준비기간 없음 | — |
| 기타 | 1일 | AI 판단 | 일반 |

**3. 사용자 조정** — 확인 화면에서 직접 늘리고 줄인다.

값의 출처(`ai` / `rule` / `rule-corrected` / `user`)를 DB에 남겨서, 어떤 값이 어디서 나왔는지 추적할 수 있다.

### 준비 시작일 역산

```
준비 시작일 = 일정 시작일 − 준비기간
```

**마감일이 아니라 일정 시작일 기준**인 것이 중요하다.
"기말고사 7/27~7/31"에 7일을 붙일 때 마감일(7/31) 기준이면 7/24가 되어
*시험 기간 한복판에서 준비를 시작하는* 꼴이 된다.
하루짜리 일정은 두 계산이 같으므로 기간형 일정까지 올바르게 처리된다.

이미 지난 날부터 시작할 수는 없으니, 마감이 안 지났으면 시작일을 오늘로 당긴다.
짧아진 준비기간은 브리핑에서 "부담"으로 잡히므로 정보가 사라지지 않는다.

### 준비 단계 분해

준비기간을 3~4단계로 쪼개고 각 단계에 계획 날짜를 균등 배분한다.

| 템플릿 | 단계 |
|---|---|
| 발표형 | 자료조사 → 초안 작성 → 리허설 → 최종 점검 |
| 작성형 | 자료조사 → 개요 잡기 → 본문 작성 → 퇴고·제출 |
| 시험형 | 시험 범위 정리 → 1차 복습 → 오답노트 → 최종 점검 |
| 학사형 | 안내문 확인 → 준비물 챙기기 → 최종 확인 |

제목에 "발표·PPT" 같은 단어가 있으면 종류 설정보다 제목을 우선한다.
같은 '과제'라도 발표형과 논술형은 준비 단계가 다르기 때문이다.
사용자가 고친 단계 구성은 **템플릿 단위로** 기억해서 다음에도 적용한다.

### 브리핑 정렬

임박도 한 축이 아니라 **임박도 + 부담** 두 축으로 정렬한다.

```
임박도 = 100 / (남은 일수 + 1)
부담   = (1 − 진행률) × 준비일수 × 30 / (남은 일수 + 1)
점수   = 임박도 + 부담 + 중요도 보너스
```

추가 입력 없이 이미 저장된 값만으로 계산되고, 화면에는 "왜 위에 있는지"를 한 줄로 보여준다
— *"준비가 밀렸어요 · D-13"*, *"아직 시작 전이에요 · D-5"*.

## 기술 스택

**백엔드** — Node.js 18+ / Express 4 / MongoDB(Mongoose 8) / Google Gemini / JWT + bcrypt / web-push / multer

**프론트엔드** — 바닐라 JavaScript 단일 파일(`index.html`), **빌드 과정 없음**, 프레임워크 없음, PWA(manifest + service worker)

프레임워크를 쓰지 않은 이유는 배포를 단순하게 유지하기 위해서다.
서버 하나가 API와 정적 파일을 모두 서빙하므로 별도 프론트 호스팅 없이 URL 하나로 동작한다.
이미지는 디스크에 저장하지 않고 메모리에서 base64로 바꿔 Gemini에 넘긴 뒤 버린다.

## 시작하기

```bash
cd smart-calendar/backend
npm install
cp .env.example .env   # 값 채우기
npm start              # http://localhost:4000
```

필수 환경변수 3개:

- `MONGODB_URI` — MongoDB 연결 문자열
- `GEMINI_API_KEY` — https://aistudio.google.com/apikey
- `JWT_SECRET` — 로그인 토큰 서명 키. 없으면 서버 재시작마다 로그인이 풀린다

선택: `GEMINI_MODEL`(콤마로 여러 개 등록하면 실패 시 다음 모델로 폴백),
`VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`(없으면 푸시만 꺼짐), `DEMO_EMAIL`/`DEMO_PASSWORD`.
자세한 설명은 `.env.example`에 있다.

### 배포

`render.yaml`이 포함되어 있어 Render에서 Blueprint로 바로 올릴 수 있다.
`MONGODB_URI`와 `GEMINI_API_KEY`만 대시보드에서 입력하면 되고 `JWT_SECRET`은 자동 생성된다.

날짜 계산은 배포 서버의 타임존과 무관하도록 전부 **KST 기준**으로 처리한다.

## 인증과 데이터 분리

**로그인해야만 쓸 수 있다.** 앱을 열면 로그인 화면이 먼저 뜨고, 그 전에는 앱 화면을 그리지 않는다.
`/api/auth/*`를 제외한 모든 API 경로가 401을 반환한다.

- 토큰은 JWT(30일), `localStorage`에 저장되므로 앱을 껐다 켜도 로그인이 유지된다
- 만료되면 조용히 정리하고 안내와 함께 로그인 화면으로 돌아간다
- `Notice` · `ScheduleEvent` · `Todo` · `PushSubscription` 모두 `user` 필드를 가지며,
  **모든** 조회·수정·삭제 쿼리에 소유자 조건이 함께 걸린다. id만 알아내 남의 일정에 접근하면 404가 난다
- 푸시 알림도 그 일정을 만든 계정의 기기에만 간다
- 공유 시트는 서비스워커가 Cache에 복사된 토큰을 읽어 붙이므로, 공유로 등록한 공지도 그 계정에 저장된다

### 데모 계정

서버가 처음 뜰 때 데모 계정이 없으면 자동으로 만들어진다(`DEMO_EMAIL` / `DEMO_PASSWORD`로 변경 가능).
로그인하면 샘플 일정이 채워지는데, **날짜를 하드코딩하지 않고 "오늘로부터 며칠"로 계산**하기 때문에
언제 접속해도 "오늘 준비 시작", "D-13", "마감 지나 회고 대기" 같은 상태가 그대로 재현된다.

다시 심는 시점은 *일정이 하나도 없을 때* 또는 *마지막으로 심은 날짜가 오늘이 아닐 때*다.
같은 날 안에서는 다시 심지 않으므로 사용 중에 만든 일정은 사라지지 않는다.

## API

접두어는 `/api`. `/api/auth/*` 외에는 모두 `Authorization: Bearer <token>`이 필요하다.

| 메서드 | 경로 | 설명 |
|---|---|---|
| `POST` | `/auth/signup` · `/auth/login` | `{ token, user }` 반환 |
| `GET` | `/auth/me` | 세션 복원 |
| `POST` | `/notices/analyze-text` · `/notices/analyze-image` | 분석 **미리보기** (저장 안 됨) |
| `POST` | `/notices/confirm` | 사용자가 누른 것만 실제 저장 |
| `GET` `POST` | `/schedule` | 일정 조회 / 수동 추가 |
| `PATCH` `DELETE` | `/schedule/:id` | 수정(준비기간 재계산) / 삭제 |
| `PATCH` | `/schedule/:id/steps/:index` | 준비 단계 완료 토글 |
| `PUT` | `/schedule/:id/steps` | 단계 구성 교체 |
| `POST` | `/schedule/:id/retro` | 마감 후 회고 |
| `GET` `POST` | `/todos` · `PATCH /todos/:id` | 할일 |
| `GET` | `/briefing` | 오늘 신경 쓸 일정, 곧 시작할 일정, 회고 대기 |
| `POST` | `/notices/quick-add` · `/notices/share-target` | 공유 시트 자동 등록 |
| `GET` `POST` | `/push/vapid-public-key` · `/push/subscribe` | 웹 푸시 |

`GET /health` → `{ ok: true }`
