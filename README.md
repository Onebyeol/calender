# 신박한 캘린더

> **마감일이 아니라, 준비 시작일을 알려주는 AI 캘린더**

카카오톡·학교 홈페이지·LMS·가정통신문에서 온 공지를 붙여넣거나 사진으로 넘기면,
AI가 공지의 성격을 읽고 **"이 일은 언제부터 준비해야 하는가"**를 역산해서 캘린더에 막대로 그려준다.

2026 SW미래채움 × AI·SW중심대학 연합 경진대회 / AI 서비스톤 출품작
분당경영고등학교 2인팀 (박한별, 신태평)

## 1. 왜 만들었나

### 문제

학생이 받는 공지는 카카오톡, 학교 홈페이지, LMS, e알리미, 가정통신문으로 흩어져 있다.
공지를 확인해도 기억에 남는 건 **마감일 하나**뿐이다.

- 그 일이 하루 만에 끝나는 일인지, 며칠을 투자해야 하는 일인지는 스스로 가늠해야 한다.
- 수행평가·공모전처럼 준비가 필요한 일정도 캘린더에는 **제출 당일 하루만** 점으로 찍힌다.
- 그래서 "언제부터 시작해야 하는지"는 아무도 알려주지 않고, 대부분 마감 며칠 전에야 알아차린다.

> **문제 정의문**
> 학생은 공지에서 마감일은 확인하지만, 그 일이 *언제부터* 준비를 시작해야 하는 일인지는
> 스스로 판단해야 하고, 이 판단은 대부분 마감이 임박해서야 이루어진다.

### 기존 서비스와의 차이

| | 기존 일정관리 AI (톡톡일정, 캘리, Trace 등) | 신박한 캘린더 |
|---|---|---|
| 공지에서 뽑는 것 | 날짜 **하나** | 마감일 + **준비 시작일** |
| 캘린더 표현 | 그 날짜에 점(point) | 준비기간 ~ 마감일 **막대(bar)** |
| 준비기간 | 개념 없음 | 공지 내용의 분량·난이도를 읽고 자동 역산 |
| 겹침 | 표시 안 됨 | 같은 주에 준비기간이 몇 개 겹치는지 레인으로 시각화 |
| 그 기간 동안 | — | 준비 단계로 자동 분해 + 체크리스트 |

일반 캘린더(구글 등)도 멀티데이 막대를 그릴 수는 있지만, **그 막대를 사용자가 직접 그려야 한다.**
이 서비스의 핵심은 그 막대가 **자동으로 나온다는 것**이다.

## 2. 주요 기능

### 공지 등록 — 3가지 경로

1. **텍스트 붙여넣기** — 공지 원문을 그대로 붙여넣기
2. **스크린샷 업로드** — 카톡·LMS 캡처 이미지를 올리면 Gemini가 OCR까지 함께 처리
3. **공유 시트 (자동 등록)** — Android는 PWA Web Share Target, iOS는 단축어(Shortcuts).
   카톡에서 공지를 길게 눌러 "공유 → 신박한 캘린더"만 하면 분석부터 저장까지 자동으로 끝난다.

### 분석 → 확인 2단계

AI가 분석한 결과를 **바로 저장하지 않는다.** 미리보기를 보여주고,
사용자가 "캘린더에 추가" / "할일에 추가"를 누른 것만 저장된다.
확인 화면에서 AI가 잡은 준비기간을 직접 늘리거나 줄일 수도 있다.

> AI가 다 알아서 정한다고 과장하지 않는 구조다. 최종 결정권은 사용자에게 있다.

### 화면 (4탭)

| 탭 | 하는 일 |
|---|---|
| **오늘** | 오늘 뭘 해야 하는지. 일별 브리핑(임박도 + 부담 2축 정렬), 오늘의 단계·할일, 곧 준비를 시작해야 할 일정 |
| **캘린더** | 월 그리드 + 준비기간 막대. 겹치는 일정은 레인에 자동 배치. 일정/할일 전환 |
| **기록** | 준비 습관 통계(제때 끝낸 단계 비율), 진행 중/지난 일정, 마감 후 회고, 종류별 분포 |
| **설정** | 계정, 일정 종류 편집(이름·색·기본 준비기간), 푸시 알림, 다크모드, 사용법 |

### 그 밖에

- **준비 단계 체크리스트** — 준비기간을 3~4단계로 자동 분해하고 각 단계에 계획 날짜를 배분. 단계 이름·개수는 직접 편집 가능
- **마감 후 회고** — "준비기간 4일로 잡았었어요, 어땠나요?"를 물어보고 계획 대비 실제 시작일을 비교
- **일정 종류 커스터마이징** — 6종 기본값에서 이름·색상·기본 준비기간·단계 템플릿을 바꾸거나 최대 10개까지 추가
- **웹 푸시 알림** — 일정이 등록되면 "언제부터 준비 시작하면 되는지"를 푸시로 알림
- **PWA** — 홈 화면에 추가하면 주소창 없이 앱처럼 실행
- **다크모드**

## 3. 동작 원리

### 전체 파이프라인

```
공지(텍스트/이미지/공유)
        ↓
  Gemini API 분석
   ├ 요약 / 중요도 / 종류 분류
   ├ 마감일 추출 (기간형이면 시작~종료)
   └ needsPrep(준비가 필요한가) + suggestedLeadDays(며칠 걸릴까)  ← AI는 '초안'만
        ↓
  종류별 규칙표가 보정  (leadTimeService.js)
        ↓
  사용자가 확인 화면에서 최종 조정
        ↓
  준비 시작일 역산 → 캘린더에 막대 + 단계 체크리스트 생성
```

### 리드타임(준비기간)을 정하는 3단계

이 서비스에서 가장 중요한 부분이다. **AI 혼자 정하지 않는다.**

1. **AI 초안** — Gemini가 공지 *내용의 분량과 난이도*를 읽고 판단한다.
   카테고리만 보고 기계적으로 정하지 않도록 프롬프트에 명시했다.

   | 공지 내용 | suggestedLeadDays |
   |---|---|
   | 설문 응답 제출, 동의서 회신 | 1 |
   | 독후감 A4 1장 | 2~3 |
   | 조사 보고서 A4 5장 이상, 팀 프로젝트 발표 | 5~7 |
   | 시험 범위가 여러 단원인 지필평가 | 7~10 |

2. **규칙표 보정** — 종류별로 허용 범위를 두고 AI 값이 벗어나면 잡아준다.
   범위는 기본 준비일수에서 자동 계산된다 (`min = 40%`, `max = min(30, max(2배, +7일))`).

   | 종류 | 기본 준비일수 | 준비 필요 판단 | 단계 템플릿 |
   |---|---:|---|---|
   | 학사일정 | 2일 | AI 판단에 맡김 | 학사형 |
   | 과제 | 3일 | 항상 필요 | 작성형 |
   | 시험 | 7일 | 항상 필요 | 시험형 |
   | 행사 | 0일 | 준비기간 없음 | — |
   | 회의 | 0일 | 준비기간 없음 | — |
   | 기타 | 1일 | AI 판단에 맡김 | 일반 |

3. **사용자 조정** — 확인 화면에서 직접 늘리고 줄인다. 이 값은 `leadTimeSource: 'user'`로 기록된다.

각 값이 어디서 나왔는지(`ai` / `rule` / `rule-corrected` / `user`)를 DB에 남긴다.
발표할 때 "이건 AI가 낸 값, 이건 규칙표가 보정한 값"을 구분해 설명할 수 있게 하기 위함이다.

### 준비 시작일 역산

```
준비 시작일 = 일정 시작일 − 준비기간
```

**마감일이 아니라 일정 시작일 기준**이라는 점이 중요하다.
"기말고사 7/27~7/31"에 7일을 붙일 때 마감일(7/31) 기준이면 7/24가 되어
*시험 기간 한복판에서 준비를 시작하는* 꼴이 된다.
하루짜리 일정은 두 계산이 같은 값이므로, 기간형 일정까지 올바르게 처리된다.

이미 지난 날부터 준비를 시작할 수는 없으므로, 마감이 아직 안 지났으면 시작일을 오늘로 당긴다.
(짧아진 준비기간은 브리핑에서 "부담"으로 잡히므로 정보가 사라지지 않는다.)

### 준비 단계 분해

준비기간을 단계로 쪼개고, 각 단계에 계획 날짜를 균등 배분한다.

| 템플릿 | 단계 |
|---|---|
| 발표형 | 자료조사 → 초안 작성 → 리허설 → 최종 점검 |
| 작성형 | 자료조사 → 개요 잡기 → 본문 작성 → 퇴고·제출 |
| 시험형 | 시험 범위 정리 → 1차 복습 → 오답노트 → 최종 점검 |
| 학사형 | 안내문 확인 → 준비물 챙기기 → 최종 확인 |
| 일반 | 내용 확인 → 준비하기 → 마무리 |

제목에 "발표·PPT·스피치" 같은 단어가 보이면 종류 설정보다 **제목을 우선**한다.
같은 '과제'라도 발표형과 논술형은 준비 단계가 다르기 때문이다.

사용자가 단계 구성을 고치면 그 구성을 **템플릿 단위로 기억**해서 다음에도 적용한다.
(카테고리가 아니라 템플릿 종류로 기억해야 "발표 수행평가"에서 고친 구성이 "독후감"에 잘못 적용되지 않는다.)

### 일별 브리핑 정렬

"임박도" 한 축이 아니라 **임박도 + 부담** 두 축으로 정렬한다.

```
임박도(urgency) = 100 / (남은 일수 + 1)
부담(load)      = (1 − 진행률) × 준비일수 × 30 / (남은 일수 + 1)     ← 준비가 밀렸을수록 큼
점수            = 임박도 + 부담 + 중요도 보너스(high 15 / medium 5 / low 0)
```

두 값 모두 이미 저장된 `endDate` / `leadTimeDays` / `steps`만으로 계산되므로 추가 입력이 없다.
화면에는 "왜 위에 있는지"를 한 줄로 설명해준다 — *"준비가 밀렸어요 · D-13"*, *"아직 시작 전이에요 · D-5"*.

## 4. 기술 스택

### 백엔드

| | |
|---|---|
| 런타임 | Node.js 18+ (개발: 24.x) |
| 웹 프레임워크 | Express 4 |
| DB | MongoDB Atlas + Mongoose 8 |
| AI | Google Gemini (`@google/generative-ai`) |
| 인증 | jsonwebtoken (JWT) + bcryptjs |
| 푸시 | web-push (VAPID) |
| 파일 업로드 | multer (메모리 저장, 파일당 8MB · 최대 4개) |

이미지는 **디스크에 저장하지 않는다.** 메모리에 잠깐 올렸다가 base64로 Gemini에 넘기고 버린다.

### 프론트엔드

| | |
|---|---|
| 구현 | **바닐라 JavaScript 단일 파일** (`index.html`, 약 2,900줄) |
| 빌드 | **없음** — 번들러·트랜스파일러 없이 그대로 서빙 |
| 프레임워크 | 없음 (자체 `setState` → 문자열 템플릿 재렌더 방식) |
| PWA | manifest + service worker (Web Share Target, 푸시 수신) |
| 폰트 | Jua |

프레임워크를 쓰지 않은 이유는 배포를 단순하게 유지하기 위해서다.
백엔드 서버 하나가 API와 정적 파일을 모두 서빙하므로, 별도 프론트 호스팅 없이 **URL 하나로 시연**할 수 있다.

렌더링은 상태가 바뀔 때마다 전체 HTML 문자열을 다시 만들어 넣는 방식이지만,
화면 구성이 바뀌지 않았을 때는 스크롤 위치를 저장·복원해서 목록이 튀지 않게 처리했다.

### 인프라

| | |
|---|---|
| 호스팅 | Render (Web Service, free plan) |
| DB | MongoDB Atlas (free tier) |
| 설정 | `render.yaml` (Infrastructure as Code) |

```
    │       └── PushSubscription.js   # 브라우저 푸시 구독
    └── frontend/
        ├── index.html                # 앱 전체 (4탭 + 모달 + 상태관리)
        ├── service-worker.js         # 공유 시트 중계, 푸시 수신

        └── icon-192.png / icon-512.png / logo-mark.png
```

## 6. 로컬에서 실행하기

```bash
cd smart-calendar/backend
npm install
cp .env.example .env
```

`.env`를 채운 뒤:

```bash
npm start
```

`http://localhost:4000` 접속. 개발 중에는 `npm run dev`(nodemon)를 쓰면 자동 재시작된다.

### 환경 변수

| 키 | 필수 | 설명 |
|---|:---:|---|
| `MONGODB_URI` | ✅ | MongoDB Atlas 연결 문자열. 없으면 서버가 부팅 단계에서 종료된다. Atlas의 Network Access에 `0.0.0.0/0` 등록 필요 |
| `GEMINI_API_KEY` | ✅ | https://aistudio.google.com/apikey 에서 발급. 없으면 서버는 뜨지만 공지 분석이 500 에러 |
| `JWT_SECRET` | ✅ | 로그인 토큰 서명 키. **없으면 서버가 재시작될 때마다 로그인이 전부 풀린다** |
| `GEMINI_MODEL` | | 콤마로 여러 개 등록하면 앞에서부터 시도하다 실패 시 다음 모델로 자동 폴백. 기본 `gemini-3.1-flash-lite` |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` | | 웹 푸시용. 없으면 푸시만 조용히 꺼지고 앱은 정상 동작 |
| `VAPID_SUBJECT` | | 푸시 서비스에 전달할 연락처 (`mailto:...`) |
| `DEMO_EMAIL` / `DEMO_PASSWORD` / `DEMO_NAME` | | 심사용 계정. 비워두면 `demo@sinbak.app` / `sinbak2026` |
| `PORT` | | 기본 4000. 배포 플랫폼이 자동 주입하므로 보통 설정 불필요 |

키 만드는 법:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

```bash
npx web-push generate-vapid-keys
```

> `GEMINI_MODEL`에 모델을 2~3개 등록해두는 걸 권한다.
> 특정 모델이 그날 불안정하거나 막혀도 시연이 멈추지 않게 하는 안전장치다.

## 7. 배포

`render.yaml`이 저장소에 포함되어 있어 Render에서 Blueprint로 바로 올릴 수 있다.

```yaml
rootDir: smart-calendar
buildCommand: cd backend && npm ci
startCommand: cd backend && npm start
healthCheckPath: /health
```

### 절차

1. Render → **New → Blueprint** → 이 저장소 연결
2. 대시보드에서 `MONGODB_URI`, `GEMINI_API_KEY` 입력 (`sync: false`라 직접 넣어야 함)
3. `JWT_SECRET`은 `generateValue: true`라 **Render가 자동 생성**하고 계속 유지한다
   → 재배포되어도 로그인이 풀리지 않는다
4. MongoDB Atlas → Network Access에 `0.0.0.0/0` 등록 (배포 서버는 IP가 계속 바뀜)
5. 배포되면 `https://<서비스명>.onrender.com` 하나로 앱 전체가 열린다

### ⚠️ 무료 플랜 주의

Render 무료 플랜은 **15분간 접속이 없으면 잠들고, 다음 접속 때 깨어나는 데 약 50초**가 걸린다.
심사위원이 URL을 열자마자 흰 화면 50초를 보게 되므로,
cron-job.org · UptimeRobot 같은 외부 서비스로 `/health`를 5분마다 핑하도록 걸어두는 것이 사실상 필수다.

### 타임존

배포 서버는 보통 UTC라서 `new Date()`를 그대로 쓰면 한국 시각 오전에 날짜가 하루 밀린다.
날짜 계산은 전부 **KST(UTC+9) 기준**으로 하도록 `leadTimeService.todayIso()`에 모아뒀다.

## 8. 로그인과 계정별 데이터 분리

계정은 JWT 기반이고, 토큰은 브라우저 `localStorage`(`sc_token`)에 저장된다.
프론트의 모든 API 호출은 `apiFetch()`를 거치면서 `Authorization: Bearer <token>` 헤더를 붙인다.
비밀번호는 bcrypt로 해시해 저장하고, 어떤 API 응답에도 실려나가지 않는다.

### 데이터 격리

`Notice` · `ScheduleEvent` · `Todo` · `PushSubscription` 모두 `user` 필드를 가지며,
**모든** 조회·수정·삭제 쿼리에 `ownerScope(req)` (= `{ user: req.userId }`)가 함께 걸린다.

- id만 알아내서 남의 일정을 고치거나 지우려 하면 **404**가 난다
- 푸시 알림도 그 일정을 만든 계정의 기기에만 간다

### 게스트 모드

토큰이 없는 요청은 `user: null`인 **게스트 데이터**를 보게 된다.
"로그인 없이 둘러보기", Android 공유 시트, iOS 단축어처럼 헤더를 붙일 수 없는 경로를 살려두기 위한 설계이며,
로그인한 계정의 일정과는 서로 보이지 않는다.

Android 공유 시트는 예외적으로, 앱이 로그인할 때 Cache Storage에 복사해둔 토큰을
서비스워커가 읽어서 붙인다. 덕분에 **로그인 상태에서 공유한 공지는 그 계정에 저장된다.**

### 상단 바 토글

상단 바 맨 왼쪽에 로그인/로그아웃 버튼이 있다.
로그아웃 상태에서는 "로그인", 로그인 상태에서는 이름 이니셜 아바타와 함께 "로그아웃"이 표시된다.

## 9. 심사/시연용 계정

```
demo@sinbak.app / sinbak2026
```

서버가 뜰 때 이 계정이 없으면 자동으로 만들어진다.
로그인 화면의 🔑 안내 박스를 누르면 자동으로 입력된다.

이 계정으로 로그인하면 `services/demoSeed.js`가 샘플 일정을 채워 넣는다.
**날짜를 하드코딩하지 않고 "오늘로부터 며칠"로 계산하기 때문에,
심사가 몇 주 뒤에 이뤄져도 항상 아래 상태가 그대로 재현된다.**

| 샘플 일정 | 보여주려는 것 |
|---|---|
| 2학기 중간고사 (준비 14일, 1/4단계) | 준비가 밀린 상태 · 긴 막대 |
| 국어 수행평가 발표 자료 제출 | **오늘부터 준비 시작** ← 서비스 핵심 메시지 |
| 과학탐구 보고서 제출 (2일 뒤 시작) | "곧 시작해요" 미리 알림 |
| 학부모 상담 주간 (3일 뒤 시작) | 겹치는 준비기간 |
| 동아리 발표회 | 준비기간이 없는 단일 일정 (대조군) |
| 영어 단어시험 (마감 지남) | **마감 후 회고** 화면 |

AI 요약과 원본 공지 텍스트도 함께 들어있어 일정 상세보기 화면까지 채워진다.

다시 심는 시점은 **"일정이 하나도 없을 때"** 또는 **"마지막으로 심은 날짜가 오늘이 아닐 때"**다.
같은 날 안에서는 다시 심지 않으므로, 심사위원이 시연 중에 만든 일정은 사라지지 않는다.

## 10. API 레퍼런스

모든 경로의 접두어는 `/api`다. `Authorization: Bearer <token>`이 있으면 그 계정의 데이터를, 없으면 게스트 데이터를 다룬다.

### 인증

| 메서드 | 경로 | 설명 |
|---|---|---|
| `POST` | `/auth/signup` | `{ name, email, password }` → `{ token, user }` |
| `POST` | `/auth/login` | `{ email, password }` → `{ token, user, seeded }` |
| `GET` | `/auth/me` | 토큰 유효성 확인 (앱 재실행 시 세션 복원) |
| `GET` | `/auth/demo-account` | 로그인 화면에 띄울 심사용 계정 안내 |

### 공지 분석 (2단계)

| 메서드 | 경로 | 설명 |
|---|---|---|
| `POST` | `/notices/analyze-text` | `{ text }` → 분석 결과 **미리보기** (저장 안 됨) |
| `POST` | `/notices/analyze-image` | multipart, field `image` → 분석 결과 미리보기 |
| `POST` | `/notices/confirm` | 사용자가 버튼을 누른 것만 실제 저장. `addEvent` / `addTodo` 중 보낸 것만 생성 |

### 일정

| 메서드 | 경로 | 설명 |
|---|---|---|
| `GET` | `/schedule` | 내 일정 전체 (월 그리드 필터링은 프론트에서) |
| `POST` | `/schedule` | 수동 추가. `leadTimeDays`를 보내면 준비기간도 함께 계산 |
| `PATCH` | `/schedule/:id` | 수정. `leadTimeDays`가 오면 원래 마감 기준으로 시작일·단계를 재계산 |
| `DELETE` | `/schedule/:id` | 삭제 |
| `PATCH` | `/schedule/:id/steps/:index` | 준비 단계 하나 완료 토글 |
| `PUT` | `/schedule/:id/steps` | 단계 구성 통째로 교체 (이름 수정·추가·삭제·순서 변경) |
| `POST` | `/schedule/:id/retro` | 마감 후 회고 저장. `{ feeling: 'tight'\|'ok'\|'loose' }` |

### 할일 · 브리핑

| 메서드 | 경로 | 설명 |
|---|---|---|
| `GET` | `/todos` | 내 할일 |
| `POST` | `/todos` | `{ title, due }` |
| `PATCH` | `/todos/:id` | 완료 토글 |
| `GET` | `/briefing` | 오늘 신경 쓸 일정(정렬됨), 곧 시작할 일정, 회고 대기, 오늘 할일 |

### 공유 자동 등록 · 푸시

| 메서드 | 경로 | 설명 |
|---|---|---|
| `POST` | `/notices/quick-add` | iOS 단축어용. 분석 + 저장을 한 번에 |
| `POST` | `/notices/share-target` | Android Web Share Target |
| `POST` | `/notices/share-upload` | 서비스워커가 multipart를 다시 만들어 전달하는 경로 |
| `GET` | `/push/vapid-public-key` | 구독에 필요한 공개키 |
| `POST` | `/push/subscribe` | 브라우저 구독 정보 저장 |

`GET /health` → `{ ok: true }` (헬스체크 · keep-alive 핑용)

## 11. 데이터 모델

### ScheduleEvent (핵심)

일반 캘린더의 이벤트와 다른 필드만 추려서 정리한다.

| 필드 | 설명 |
|---|---|
| `startDate` / `endDate` | 막대의 시작과 끝. **준비기간이 붙으면 startDate가 앞으로 당겨진다** |
| `originalStartDate` | 준비기간 적용 전 원래 일정 시작일. 나중에 준비기간을 조정할 때 기준이 된다 |
| `needsPrep` | 준비가 필요한 유형인가 |
| `leadTimeDays` | 최종 적용된 준비기간(일) |
| `leadTimeSource` | 이 값의 출처: `ai` / `rule` / `rule-corrected` / `user` |
| `stepTemplateKey` | 어떤 단계 템플릿에서 나왔는지 (사용자 편집 기억용) |
| `steps[]` | `{ title, plannedDate, done, doneAt }` — 준비 단계 체크리스트 |
| `retro` | `{ answeredAt, feeling, actualLeadDays }` — 마감 후 회고 |
| `aiSummary` / `sourceType` / `sourceContent` | 상세보기에서 AI 요약 + 원본 공지를 보여주기 위한 필드 |

`doneAt`(실제 체크 시각)을 남기는 이유는, 회고에서 **계획한 시작일과 실제로 시작한 날을 비교**하기 위해서다.

### 그 외

- **User** — `name`, `email`(unique), `passwordHash`, `isDemo`, `demoSeededOn`
- **Notice** — 원본 공지 + AI 분석 결과. 일정/할일에서 역추적 가능
- **Todo** — `title`, `due`, `done`
- **PushSubscription** — 브라우저 구독 정보 (`endpoint` unique)

일정 종류 설정·리드타임 선호값·단계 편집 기록은 서버가 아니라 **브라우저 localStorage**에 저장되고,
분석 요청 때 함께 전송된다 (`sc_categories`, `sc_lead_pref`, `sc_step_pref`).

## 12. PWA · 공유 연동

### Android

`manifest.json`의 `share_target`으로 등록되어, 홈 화면에 추가하면 **시스템 공유 시트에 앱이 뜬다.**
카톡 공지를 길게 눌러 공유하면 분석·저장까지 자동으로 끝나고 앱이 결과와 함께 열린다.

제조사마다 파일 필드명과 전송 방식이 달라서, 서비스워커가 formData를 먼저 읽고
새 multipart 요청으로 다시 만들어 서버에 전달한다.
(원본 스트림을 그대로 넘기면 일부 기기에서 `Unexpected end of form`이 발생한다.)

### iOS

Web Share Target을 지원하지 않으므로 **단축어(Shortcuts)** 로 `POST /api/notices/quick-add`를 호출한다.

### 푸시 알림

- 웹 푸시(VAPID) 기반. 앱이 꺼져 있어도 서비스워커가 알림을 띄운다
- **iOS는 "홈 화면에 추가"를 한 상태에서만 동작한다** (Safari 제약)
- 알림 내용은 마감일이 아니라 *"OO부터 준비 시작하면 돼요"*

## 13. 현재 범위에서 빠진 것

솔직하게 적어둔다.

- **시각 기반 알림 스케줄러** — 푸시 발송 자체는 동작하지만(일정 등록 시 + 1분 뒤 테스트 알람),
  "준비 시작일 아침 8시에 알려주기"처럼 정해진 시각에 보내는 잡은 아직 없다.
  Render 무료 플랜은 유휴 시 잠들기 때문에 in-process cron만으로는 부족하고,
  외부 cron이나 Render Cron Job이 함께 필요하다.
- **변경 공지 자동 반영** — 이미 등록된 일정의 날짜가 바뀌었다는 공지를 자동으로 찾아 갱신하는 기능.
  난이도 대비 시간 리스크가 커서 제외했다.
- **비밀번호 찾기** — 메일 발송 서버가 없어서 화면에서 뺐다.
  동작하지 않는 버튼을 두는 것보다 없는 편이 낫다고 판단했다.
- **카카오톡 API 직접 수집** — 플랫폼 정책상 불가능. 공유 시트 연동으로 대체했다.
